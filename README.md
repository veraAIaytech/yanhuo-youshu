> **不抢阿姨的锅铲，只补她的记性、算盘和喇叭。**

> 给个体小摊主的 AI 经营副驾：用她自己摊位的数据，做备货预测、熟客档案和出摊预告。

## 一、项目背景：凌晨四点半的三道难题

煎饼摊张姐凌晨出摊、十点收摊，二十年手艺，靠经验吃饭。但她每天都在三道难题上吃亏：

1. **备货靠猜** —— 薄脆放到中午就不脆，备多了是浪费，备少了是缺货，一买一卖都是真金白银；
2. **熟客靠脑记** —— 「张叔双蛋不要香菜」记得住三五个，记不住三十个，而熟客就是她的全部生意；
3. **顾客会跑空** —— 家里有事没出摊，老顾客白跑一趟。她欠的不是一天生意，是人情。

点餐软件很多，但没有一个是为「她」做的：连锁 SaaS 服务的是多门店企业，个体户要的不是管理软件，是**一个懂她这个摊的助手**；连锁有数据团队做预测，**个体户没有数据团队**。烟火有数让 AI 直接当她的数据团队——而且数据全部来自她自己的摊。

## 我们的愿景

> **不想做漂亮夺眼球的玩具，只想减负和变现。**

- **变现是认真目标。** 不想赚钱的兵不是好兵。商业化可遇不可求，但路径已经铺好：从零成本的官方商家收款码，到正规签约的支付接口，三阶段落地路线见「后续计划」——机会来的时候，接得住。
- **减负是底线。** 如果变现暂时没来，至少让 AI 替摊主记熟客、算备货、喊出摊，把她从最累的三件事里解放出来。AI 赋能不是替代手艺，是给人减负、切实解决真实需求。
- 本项目的功能取舍一律按这个次序：**先有用，再好看，最后才谈花哨。**

## 二、目标用户

一个摊位、没有雇人、不会用复杂软件的个体餐饮经营者：煎饼摊、早餐车、夜宵摊、水果摊。以「自提 + 线下收款」为主要经营方式，月流水万元左右，对成本极敏感。

## 三、产品：一摊三端

| 端 | 路由 | 功能 |
|---|---|---|
| 🧑‍🤝‍🧑 **顾客端** | `/` | 出摊预告（防跑空）· 菜单多规格 · 购物车 · 自提时段预定 · 收银台（自动识别微信/支付宝/浏览器环境）· 取餐号 |
| 🪔 **阿姨端** | `/ayi` | 晨报：明日备货建议（含说人话的理由）· 今日熟客时间表 · 线上订单推进 · **收摊语音记账**（「今天卖了八十个」自动结构化） |
| 📈 **数据飞轮** | `/board` | 14 天预测 vs 实际曲线 · 误差收敛 · 浪费减少指标 · 「时间快进」演示器 |

另有 iPad 招揽看板 `/kiosk`（全屏轮播 + 实时数据 + 动态体验二维码）和自动路演幻灯片 `/deck`。

## 四、三个创新点

**① 记性 —— 熟客档案**：AI 替摊主记住每个熟客的口味和到点规律。《深夜食堂》最动人的是老板记得熟客口味——我们把这份记性交给 AI，**只服务这一个摊，数据匿名、不出摊**。

**② 算盘 —— 备货预测**：预测模型融合星期规律 × 天气 × 开学/节假日日历，并把每个数字翻译成摊主能懂的人话（「明天降温又开学，备 132 份」）。演示数据中，14 天误差从 ±30% 收敛到 ±8%，日均食材浪费减半。
冷启动的关键是**语音记账**：小商户最缺的是录数据的时间，收摊时对手机说一句话，GLM 解析成结构化数据——不新增任何录入负担，飞轮才转得起来。

**③ 喇叭 —— 出摊预告**：出不出摊、几点出摊、卖完即止，顾客订阅即可收到；AI 还会根据预测建议出摊时间。一个延伸的愿景是：预测到单量低的日子，AI 建议休息——**帮个体户拿到双休日**。

## 五、技术栈

- **前端/服务端**：Next.js (App Router) + TypeScript + Tailwind CSS v4，移动端优先（44px 触控目标、`100dvh`、iPhone 安全区、`prefers-reduced-motion`）
- **AI**：GLM（z.ai）语音记账解析 + 晨报人话生成；全部调用带确定性兜底，离线/无 Key 时演示永不掉线
- **支付架构**：`PaymentProvider` 适配层（`createOrder / pay / parseCallback`），当前实现 `MockProvider`，落地时新增微信/支付宝官方 Provider **业务零改动**；前端 UA 环境检测三分支
- **工程可靠性**：金额服务端重算（不信前端）、订单幂等防重复提交、订单状态机、数据合成可重放（确定性种子）
- **数据**：黑客松为内存态 + 合成数据（零基础设施）；模型与字段与落地版数据库对齐，可平移

## 六、团队分工

个人参赛。采用 **人类出题、AI Agent 结对施工** 的方式：人负责问题定义、体验验收和「烟火气」把关；AI Agent 负责架构选型、全栈编码、合成数据与部署——这是赛道鼓励的「Agent 协同新范式」的一次完整实践。

## 七、开发过程

34 小时从零到可体验：技术选型调研（GitHub 点餐类开源项目横评）→ 数据模型与确定性合成数据（14 天营业史 + 熟客档案）→ 三端界面与支付适配层 → GLM 接入（兜底解析支持「八十」等中文数字）→ 构建验证与 API 端到端冒烟 → Vercel 部署 → iPad 看板与自动幻灯片。所有关键决策有留档，详见 `docs/PLAN.md`。

## 八、后续计划（真实落地路线，已验证可行）

| 阶段 | 内容 | 成本 |
|---|---|---|
| 阶段 0（赛后即用） | 摊位放微信/支付宝官方商家收款码（≈0 费率），小程序做预告/预定/记账/预测，收款靠语音播报人工确认 | ≈0 |
| 阶段 1 | 办理个体工商户营业执照 → 商家收款码 → H5 按环境展示对应码 +「我已付款」核销 | 工本费 |
| 阶段 2 | 签约微信支付商户号 + 支付宝当面付，适配层换 Provider（回调验签/幂等/对账）；底座 fork 开源 yshop-drink（MIT，含点餐/自取/预定/微信支付） | 费率约 0.6% |

商业路径：单摊年费制（一个月的早餐钱）→ 早餐车/夜宵摊可复制 → 同商圈多摊数据互助网络。
合规已查明：个人主体小程序不能开通微信支付、不能上餐饮类目，故阶段 1 需个体工商户营业执照。

## 本地运行

```bash
npm install
npm run dev        # http://localhost:3000
npm run build && npm start   # 生产版
```

环境变量（可选，不设也能跑，走兜底）：`ZAI_API_KEY`、`ZAI_API_BASE`、`ZAI_MODEL`。

## 现场体验（局域网方案）

1. 笔记本：`npm run start -- -H 0.0.0.0 -p 3000`
2. 手机/ iPad 连笔记本热点，浏览器访问 `http://<笔记本局域网IP>:3000`
3. 看板页（`/kiosk`）二维码会自动指向当前访问地址，评委扫码秒开
4. 演示数据重置：面板页「↺ 重置演示数据」按钮
